# Plan previo de publicación del incremento de rendimiento

28/10/2026. La API de entrega conserva OpenAPI 0.11.0 y esquema V23. El servicio está con mínimo cero y máximo uno; Prometheus y Grafana locales están apagados. Las optimizaciones no requieren migraciones, dependencias nuevas o cambios de configuración. Este documento precede a la construcción y al despliegue nuevos.

## Condiciones y secuencia

1. Congelar las fuentes de autenticación, citas y clínica y sus pruebas. Ejecutar un único `mvnw clean verify` con Java 25, PostgreSQL local de pruebas y variables de runtime excluidas del proceso hijo, conservando únicamente las credenciales locales de pruebas necesarias. Verificar reportes sin fallos, errores u omisiones; validar ejemplos OpenAPI, snapshot versionado y gates negativos. Archivar reportes/contrato y huellas fuera de Git.
2. Mantener el corte desplegado anterior y sus seis incumplimientos de latencia. Confirmar Git limpio respecto de los archivos que se enviarán, publicar los commits por PR y verificar el check requerido del mismo SHA. Integrar únicamente cuando protección de main y CI lo permitan. No forzar ramas, omitir checks o modificar el trabajo de auditoría.
3. Comprobar consumo semanal antes de publicar/compilar. Con 20% o menos restante, guardar el checkpoint y detener este trabajo conforme a la instrucción del usuario. El contador es compartido y se observa periódicamente, no es un límite global de la cuenta.
4. Identificar el commit integrado y enumerar `gcloud meta list-files-for-upload`. Admitir solo `.gcloudignore`, `.dockerignore`, Dockerfile, pom, Maven Wrapper y `src/main`. Comprobar cada archivo contra su blob de Git normalizado para LF/CRLF y guardar además SHA256 de los bytes exactos de subida. Rechazar material criptográfico, credenciales, output, tests o archivos privados.
5. Reutilizar Cloud Build regional `us-central1`, la cuenta dedicada `grownupsvet-build` y el bucket privado `grownupsvet-build-source-268681790250` ya verificados con el build histórico. Enviar `scripts/cloudbuild.yaml` y un tag único derivado del commit. No crear identidades, buckets, repositorios, permisos o recursos adicionales ni actualizar la facturación. La primera lectura global del build histórico no lo encontró; la lectura con región explícita confirmó cuenta, bucket y digest. Usar siempre proyecto y región explícitos.
6. Guardar el ID de build y esperar ese mismo proceso hasta estado terminal. Exigir SUCCESS e imagen/digest esperados. No repetir un build porque una observación expire; volver a consultar el mismo ID. La construcción no cambia el tráfico. Conservar manifiesto y digest del origen para una recuperación compatible.
7. Antes del despliegue, comprobar que no exista otro cambio operativo en curso. Leer la configuración vigente de Cloud Run de forma privada y revisar metadatos saneados: revisión, imagen, generación, tráfico, perfiles, secretos por referencia, probes, identidad, CPU/recursos y escalado. Si hay una diferencia ajena al incremento, reevaluarla antes de modificar la imagen.
8. Usar el helper revisado `deploy-google-cloud.ps1` en modo **ImageOnly**, primero offline y después con Execute, digest inmutable y `ExpectedContractVersion=0.11.0`. El modo ejecutable actualiza exclusivamente `--image` y compara huella de configuración antes/después; no usar la plantilla histórica ni reconstruir variables. En el proceso hijo se puede añadir el SDK portátil al PATH sin cambiar la configuración del equipo. Mantener mínimo cero y máximo uno, token de monitoreo, admisión de login V23, referencias JWT/SMTP/BD y probes.
9. Verificar revisión lista, tráfico único 100%, digest, configuración conservada y contrato público. El único cambio admitido al comparar OpenAPI generado con producción es `servers`, validado primero contra la URL de backend configurada; no ignorar diferencias de rutas, esquemas o permisos. Identificar la revisión exacta en las muestras posteriores.
10. Ejecutar el plan postpatch revisado con fixtures ficticios y un run separado. Declarar calentamiento, perfil y N antes de medir; mantener errores, resultados inciertos y SLO incumplidos. Los replays no cuentan como escrituras nuevas y una cita futura no se finaliza anticipadamente. No cambiar reloj, fechas mediante SQL ni reabrir atenciones. Los checks de correo reales requieren mantener una instancia durante su ventana, mediante la autorización operativa ya aprobada.
11. Encender temporalmente el monitoreo local para verificar scrape fresco, etiquetas y paneles de la revisión nueva. Al terminar las pruebas activas, apagar los procesos locales y comprobar mínimo cero/máximo uno. No dejar scrapes periódicos que mantengan despierta la API.

## Evidencia y criterio de cierre

La entrega relacionará commit → manifiesto exacto de fuentes → build → digest → revisión → contrato/CI → resultados de aceptación y métricas. La configuración y las credenciales completas permanecerán fuera de Git. Una imagen construida, CI verde o una reducción de sentencias no demuestra por separado el objetivo completo: las operaciones medidas y las garantías funcionales deben verificarse en el alcance que declaran.

Los backups y su automatización del 13 de noviembre permanecen intactos. No hay downgrade de Flyway ni restauración destructiva. La imagen anterior admisión/V23 se conserva como referencia compatible; no se vuelve a una imagen P3 previa al limitador de login. Cualquier fallo de verificación se informa con su estado real y se investiga antes de declarar el backend cerrado.
